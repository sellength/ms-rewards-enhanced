## 2. 关于 Gemini API Key：正常传输与风险边界

**正常行为**：用户选择 Gemini 服务商、配置 Gemini API Key 后，调用 Gemini API 必须把该 Key 作为认证凭据发送到配置的 Gemini 端点。当前服务商目录中的 Gemini 地址为 `https://generativelanguage.googleapis.com/v1beta/openai`。这本身不是“密钥外传”漏洞；对 OpenAI、自定义网关等也同理，用户明确选择的服务商需要接收其对应凭据。请求主题、搜索词等业务内容是否发送，应另按隐私契约评估，不能把“发送 API Key”与“发送账号 Cookie/TOTP”混为一谈。

**当前风险**：`web.mjs` 的 `/api/ai/test`、`/api/ai/fetch-models` 接收请求中的 `profileId` 和 `baseUrl`。当请求未提供新 Key 时，它们会读取该 Profile 已保存的 Key，随后 `scripts/api/profileManager.mjs` 向请求指定的 `baseUrl` 发送带 `Authorization: Bearer <Key>` 的请求。若未授权调用者能够访问本地控制 API，就可把已保存的 Gemini Key 发往其控制的地址。风险成立的关键是**调用者可覆盖已保存密钥的目标地址**，不是 Gemini 正常接收 Gemini Key。自定义网关是现有功能，不能简单全部禁用。

**目标规则**：已保存 Key 只能用于该 Key 经用户确认并保存时绑定的服务商和规范化目标地址。请求体临时覆盖地址时，不得自动补入已保存 Key；用户确实更换自定义网关时，应明确保存新地址及与之配套的 Key，经过验证后再使用。禁止把密钥发往非预期协议、主机、端口或重定向目标。不能仅靠前端输入限制，必须在服务端执行。

**验收用例**：

1. 合成 Gemini Key 请求绑定的 Gemini 地址，模拟服务看到认证头；真实外网请求次数为零。
2. 同一 Profile 带恶意覆盖 `baseUrl` 且省略 Key，服务端拒绝，恶意模拟服务收到零请求、零字节密钥。
3. 自定义网关经用户明确保存地址和新 Key 后可以正常测试；更换地址但沿用旧保存 Key 被拒绝。
4. 目标地址规范化、HTTP 明文、跨主机重定向及无效 URL 的行为有测试；错误响应和日志不回显 Key。

## 3. 逐项整改与验收

### S1（严重）：Web 控制 API 的访问控制

**证据**：`web.mjs` 约 1955—1968 行对所有请求设置 `Access-Control-Allow-Origin: *` 且无统一鉴权；约 3117 行 `server.listen(PORT)` 未指定回环地址。`/api/account`、`/api/run`、`/api/account/logout`、`/api/profiles/*` 等均可达。

**要求**：默认只绑定 `127.0.0.1`；控制接口和敏感读取接口必须有服务端鉴权，并拒绝不可信 Origin/Host。写接口还需防 CSRF；SSE、首次打开页面、重连和正常本地 UI 必须在同一安全模型下可用。仅改 CORS 或仅绑定回环不足以防同机恶意页面及本机其他进程。不得在 URL、源码或控制台日志中暴露长期令牌。

**验收**：未授权的本机 HTTP 请求、外部 Origin 请求、错误 Host 请求均不能读敏感数据或产生执行副作用；授权本地页面可以使用账户、任务、配置和 SSE；监听地址通过 socket 级测试确认。现有名为“local-only”的源码字符串断言不能代替网络行为测试。

### S2（严重）：AI 密钥目标地址绑定

按第 2 节规则修复 `web.mjs` 与 `scripts/api/profileManager.mjs`，并覆盖 `/api/ai/test` 与 `/api/ai/fetch-models` 两条路径。服务端鉴权与地址绑定都必须存在，不能以其中一项替代另一项。

### S3（高）：账户敏感字段与静态存储

**证据**：`web.mjs` 约 2609 行在 `GET /api/account` 返回 TOTP 明文；约 3006—3017 行把密码和 TOTP 写入 `.env`，且写入时未指定权限。`src/util/ProfileCrypto.ts` 的 AES-GCM 随机 IV 和认证标签基本正确，但密钥来自可推知的机器信息及代码内固定盐，不是独立保密的主密钥。

**要求**：API 不返回 TOTP 或密码明文；页面以“已配置”状态及明确的替换/清除操作呈现。评估使用系统密钥链或用户提供的主密钥保护持久化凭据；给出兼容现有 `.env` 的安全迁移与失败恢复方案，不能静默丢失账号。所有新写入敏感文件限制为仅当前用户可读写。文档准确区分加密、混淆、权限保护及无法承诺的防护能力。

**验收**：API 响应、页面 DOM、日志均不含合成 TOTP 明文；旧格式迁移和权限检查通过；错误密钥或损坏数据安全失败，不回退为明文输出。

### S4（高）：PC 与移动会话隔离

**证据**：`src/index.ts` 约 586—594 行把移动 Cookie 清洗后注入桌面浏览器；约 1186—1188 行把清洗后的移动 Cookie 赋给桌面 Cookie。`sanitizeCookies` 仅排除部分已知名称和值，不能证明跨端隔离。

**要求**：PC 与移动分别加载、缓存、持久化自己的 Cookie、Token、Session 和指纹；移除跨端复制。若既有登录流程依赖该复制，须重新设计明确的 PC 登录或会话恢复路径，不能通过放宽隔离维持表面功能。官方积分与完成真值口径不改。

**验收**：给两端合成不同的同名认证 Cookie，PC 请求/浏览器环境绝不含移动值，移动请求亦不含 PC 值；覆盖 API 搜索和浏览器搜索分支；登录状态与任务选择仍按原终端工作。

### S5（高）：多 Profile 注销一致性及缓存清理

**证据**：`web.mjs` 的当前会话读取优先使用活动 Profile；注销约 2645—2653 行却以 `.env` 账号邮箱删除会话，只删除通用 `daily_state.json`、`mobile_state.json`。按 Profile 的 `daily_state_<id>.json`、`mobile_state_<id>.json` 仍可能保留。SQLite `DELETE` 也不能证明物理不可逆抹除。

**要求**：以当前活动 Profile 的确定身份执行注销，并一次性清理该账号桌面/移动会话、关联元数据、对应展示缓存与运行时状态；其他 Profile 数据保持不变。明确是否保留该 Profile 的 AI 设置；产品文案应与实际删除范围一致。对 SQLite 仅承诺逻辑删除，若要求介质级清除须另行设计并验证。

**验收**：准备 A/B 两个合成 Profile，切到 B 后注销只清除 B 的指定数据，A 不变；重复注销幂等；任务进行中返回 409 且无部分清理；失败不显示“已全部清除”。

### S6（中）：缓存净化不得跨账号批量改写

**证据**：`web.mjs` `/api/cache/clear` 约 2532 行每端只选一条 `sessions` 记录，却在约 2541 行按 `platform` 更新该端所有账号的记录，可能将一个账号的 storage state 写给其他账号。

**要求**：按明确的账号与终端主键读取和更新同一条记录；如果 UI 意图为“当前账号清理”，不得遍历或改写其他 Profile。保留原有云同步授权边界。

**验收**：A/B 账号有不同合成 Cookie，清理 B 后 A 字节级不变，B 只剥离规定字段；错误平台参数不触发任何修改。

### S7（中）：安全跳过策略声明与执行一致

**证据**：`src/index.ts` 约 750—778 行允许 `contintueOnBotWarning=true` 后继续执行；审计材料却把 `skip_safety_guard` 描述为无条件最高优先级熔断。其他跳过策略分布在不同执行器，不能只凭日志标识认定统一门控存在。

**要求**：按 `REQ-CARD-TAXONOMY-AND-SKIP-POLICY-20260930` 和接口注册表核对六项策略逐条的适用端、触发条件及执行副作用。若产品允许显式覆盖告警，文档和 UI 必须准确说明；若契约要求强制停机，则服务端阻断，不能只改日志。不要擅改官方积分或完成真值。

**验收**：每项策略使用合成官方状态验证“零不应发生的写请求”；覆盖告警开关的两种配置；离线结果不宣称真实风控有效。
